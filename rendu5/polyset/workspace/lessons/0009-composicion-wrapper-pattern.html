Composición / wrapper pattern (set)

Objetivo: entender por qué sb(other.sb) — copiar solo el puntero — es correcto en set, cuando la misma línea era el bug del Bloque 2/3 en array_bag.

HAS-A, no IS-A

Todo lo anterior (Bloques 4-7) era herencia: searchable_array_bag es un array_bag. set es distinto — no hereda de searchable_bag, solo guarda un puntero a uno. Eso es composición: set tiene un searchable_bag*, no es un searchable_bag.

La misma línea, dos conclusiones opuestas

Lo que decide si copiar un puntero es un bug o el diseño correcto no es el puntero en sí — es quién posee el recurso al que apunta.

array_bag
(dueño del recurso)
data = src.data; → dos objetos creen poseer el mismo array. Ambos destructores hacen delete[] data → double free (Bloque 2/3).
set
(vista, no dueño)
sb(other.sb); → dos set apuntan al mismo searchable_bag externo, a propósito. Ningún destructor de set hace delete — no hay conflicto de propiedad porque set nunca reclama la propiedad.

El riesgo cambia, no desaparece

Sin dueño compartido no hay double free — pero aparece el riesgo inverso: si el objeto que posee el searchable_bag muere antes que el set que lo envuelve, sb queda colgando (dangling pointer): 

set* s;
{
    searchable_array_bag bag;
    s = new set(bag);
} // bag se destruye aquí — s->sb queda inválido
s->insert(42); // usa un puntero colgante

El contrato implícito de set: el searchable_bag envuelto debe vivir al menos tanto como cualquier set que lo use. En C++ moderno esto se documentaría marcando sb como puntero no-propietario (regla R.3 de las C++ Core Guidelines: "a raw pointer is non-owning" — el patrón exacto que ya implementaste).

Caso resuelto — checkpoint final

Pregunta: misma línea de código (copiar un puntero), Bloque 2/3 dice que es un bug, Bloque 9 dice que es correcto. ¿Qué cambia?

Tu respuesta: quién posee el recurso. array_bag lo crea y debe liberarlo — copiar el puntero produce doble propiedad accidental. set nunca lo posee — copiar el puntero es una vista compartida intencional. Identificaste además, sin que se pidiera, el riesgo que sí introduce este patrón: dangling pointer si el dueño externo muere primero.
